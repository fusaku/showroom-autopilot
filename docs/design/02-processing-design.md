# 02 处理详细设计书

## 1. 检测与数据库写入

入口：`monitor_showroom.py`。选择实例分片/单成员/默认成员，创建绑定来源地址的异步 HTTP 客户端，请求房间状态。`check_single_member()` 将结果写入容量 1000 的同步队列，并更新内存中的上次状态。

后台线程取出批次，按 MEMBER_ID 保留最后一项，执行直播状态 MERGE；根据前后直播状态维护历史并调用录制器分配。源码目标轮询间隔为 5 秒，HTTP 超时为 10 秒；不代表每次运行必定在 5 秒内结束。

当前特殊行为：HTTP 非 200/JSON 解析失败返回未知，但一般异常分支返回下播；失败批次没有可靠持久化重放。本文记录原行为，不在文档生成过程中修改。

另需核对：初始实例分片后，主循环重新获取成员列表并覆盖 MEMBERS，不能仅凭初始化逻辑断言全程保持相同分片。

## 2. 实例分配

`assign_recorder()` 查询成员数据库 ID，优先使用已有启用分配，否则按 active 实例的启用分配数量排序，插入分配。`clear_assignment()` 在结束事件中删除自动分配。

当前分配算法按数量选最小负载，未在该选择语句中按 MAX_CAPACITY 做容量筛选。分配模块内部提交，不能把它和状态/历史写入描述成单一原子事务。无可用实例时返回失败，不应在页面显示“已开始录制”。

## 3. 录制进程

`read_all_live_status()` 联查直播状态、成员和分配，筛选本实例且已启用的直播。`monitor_all_members()` 扫描 `showroom.py` 进程，处理重复进程与恢复，再为符合条件的成员启动进程。

启动参数以成员英文名传给外部抓流脚本，日志写入 LOG_DIR 下的 showroom 目录。`member_processes` 保存 PID、上次直播时间和接管标识等内存状态，不是可供远程网页直接读取的数据库表。

当前 smart-start 明确排除 `hashimoto_haruna`；`restart_handler.py` 存在基于成员服务的恢复逻辑。该成员实际由何种服务启动须核对，不能只监控 smart-start 就覆盖全部录制。

**出站网络与分流机制**：早期录制子进程默认使用录制机单一主 IP 出口，并发录制易触发 Showroom CDN 频控限制。当前设计支持借用 1C 监控机的 30 个辅助 IP 作为流式中转代理，通过哈希算法将成员分配至不同代理端口，仅在启动子进程时局部注入代理环境变量；内置 0.05 秒端口健康检测，若代理不可达则自动平滑降级为直连；上传流程强制剔除代理，确保 YouTube 认证严格走固定出口（详见第 09 章）。

## 4. 3C 校验与同步

checker 寻找稳定 TS，使用 FFprobe 校验，利用成员范围内的指纹去重。指纹主要由前 512KB MD5 和文件大小构成，保存在进程内。结束收尾排序后写 `filelist.txt`；无有效分片也会写含注释的清单，因此文件存在不等于有效媒体存在。

有效分片、结束清单和字幕通过同步模块处理。同步策略：

| 条件 | 行为 |
|---|---|
| SYNC_MODE=off | 不同步 4C，本地上传选择允许处理 |
| SYNC_MODE=main | 按主推成员过滤 |
| SYNC_MODE=all | 面向全部成员，仍受分辨率等检查控制 |
| 明确检测到 TS/视频高度 ≥720 | 源 TS 不向 4C 转码链发送；上传选择倾向本地 |
| 分辨率未知 | 继续按成员/模式判断，不保证实际同步成功 |

`sync_filelist_and_audit()` 处理清单相关检查及同步。SSH 连接可用、目标路径、模式和成功结果均是传输完成的必要条件，不能只看源端日志中的意图。

## 5. 4C 加工与合并

`checker_4c` 读取 incoming，按 TS 序号连续性分段，每组最多 500 片；未到最后阶段的小组暂缓。upscaler 生成 `chunk_起始序号_结束序号.mp4`，结束检查要求来源清单、processed 目录及最后分片对应产物等条件。

收尾生成 processed 下的 `filelist.txt`，交给 merger。3C 和 4C 的目录分组算法并非完全一致：3C 使用 TS 时间信息，4C 当前主要使用目录 ctime 的四小时间隔。页面关联场次时不能直接假定两者分组恒等。

merger 使用文件锁并运行 FFmpeg concat；成功后为来源目录写 `.merged`。当前直接输出最终文件，存在文件会被跳过；“文件存在”不宜作为完整性证明。

## 6. 上传与发布

upload_youtube 保留三个认证入口，调用公共认证函数。媒体处理涉及账号选择、上传会话、失败重试、配额记录、视频状态校验、播放列表及本地上传信息保存。

取得并通过当前校验路径的 video_id 后写 `.uploaded`。当前短轮询超时可能视为通过，因此该标记不能直接解释成远端处理最终成功。账号配额耗尽日期保存在内存，重启会失去这份内存记录。

对象存储上传及 GitHub Pages 发布为配置相关路径；字幕处理在独立模块中实现。删除是否执行由配置决定，当前本地 YOUTUBE_DELETE_AFTER_UPLOAD=False；服务器值待核实。

## 7. 并发与状态边界

监控采用 asyncio 与数据库线程；校验采用线程池；合并和上传使用 flock。`file_lock.py` 从原来两份完全相同实现抽取，锁目录、命名和释放策略未改。它是文件锁，不是数据库任务锁，也不是跨机器的全局锁。
