## 第一阶段只读验收

| 场景 | 通过标准 |
|---|---|
| 成员列表 | 分页总数与同条件 DB 查询一致；组合/启用筛选正确 |
| 直播列表 | 同时展示 CHECK_TIME；旧记录不当作实时状态 |
| 数据库故障 | 显示不可用或过期，不把成员数/直播数误报为零 |
| 权限 | 后台账户不能修改业务表；浏览器没有数据库凭据 |
| 后台停止 | 现有检测、录制、同步和上传继续运行 |
| 查询开销 | 试运行前后测量 DB 延迟及连接数，无持续排队；先约定可接受阈值 |

## 状态采集验收

录制进程正常写入、进程存在但 TS 不增长、进程不存在、主机失联、权限不足、标记已被清理等场景应分别显示合理状态。用隔离目录和模拟采集故障测试，不为测试破坏正在录制的进程。

4C 观察应区分等待来源清单、加工片段出现、合并标记及上传结果。只看到一个 chunk 不显示整场完成。无法关联场次保留未知，不把不同日期同成员目录合并显示。

## 成员写入验收（后续）

1. 添加完整成员和最小必要字段成功，关联关系正确；缺字段/重复 ID/无效组合明确拒绝。
2. 模拟任一关联写入失败时，成员与关联配置一致回滚。
3. 相同请求重试不重复创建成员；编辑冲突不覆盖其他工具的修改。
4. 生效提示准确；不以“DB 提交”证明抓流端已加载。
5. 停用/归档保留历史，不自动操作进程、媒体或上传。
6. 业务库已提交但审计写入失败可追踪和对账。

## 当前实现注意点

这些是代码边界，不表示用户当前生产已发生故障，也不作为本次重构任务：

- 配置快照与新增成员生效存在不确定性。
- 数据库直播状态、实例分配和真实进程不是同一种状态。
- 3C/4C 的分组规则、标记和实际完成状态不能简单等同。
- 源脚本导入可能执行日志、配置与数据库初始化；后台应编写独立数据适配器。
- 根目录 manage_members.py、update_playlists_from_yaml.py 的 config 导入依赖路径环境，不能直接当作后台库使用。
- 原系统的异常恢复与清理风险应单独评估，不混入“可视化后台”实施范围。
